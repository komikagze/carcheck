# 1. ЧТО МЫ ХОТИМ СДЕЛАТЬ

Сайт, где по номеру израильского автомобиля можно проверить машину перед
покупкой. Открыт всем, без логина, бесплатно.

Два разных по природе блока информации:

### 1.1 Живой поиск (работает с самого начала)
Марка, год, цвет, пробег на последнем техосмотре, VIN, тип владения, отзывы
(ריקול), комплектация, цена по прайсу. Всё это **есть в data.gov.il прямо
сейчас**, запрашивается в момент поиска и никак не хранится у нас.

### 1.2 Накопленная история (главная ценность, ради неё всё затевалось)
Государство публикует только **текущий срез**: «пробег на последнем тесте —
129 982». Каким он был год назад — нигде не публикуется и нигде не хранится.

Поэтому мы **сами снимаем срез раз в неделю и копим разницу**. Это даёт то,
чего нет ни у одного сервиса:

- **история пробега по датам техосмотров** — видно динамику;
- **скрутка одометра** — пробег уменьшился между снимками, так не бывает;
- **смена номера двигателя** — двигатель меняли;
- **журнал изменений** — когда, какое поле, было → стало (цвет, VIN, топливо,
  тип владения, модель двигателя);
- **разбор истории владения** — сколько рук, сколько времени у каждой,
  сколько раз машина прошла через перекупщика.

### 1.3 Ограничение, встроенное в замысел
Данные по **одной** машине должны быть доступны любому желающему без логина.
Но **выгрузить всю базу целиком** должно быть непрактично. Это не паранойя, а
осознанное условие задачи с самого начала.

## 2.2 Что делает Cloudflare, а что Turso — ЭТО ГЛАВНАЯ ПУТАНИЦА

Их роли часто путают, потому что Cloudflare мы **и используем, и частично
отказались**. Разложим:

| | Роль | Статус |
|---|---|---|
| **Cloudflare Workers** | Хостинг сайта: раздаёт статику из `public/` и выполняет серверную функцию `worker/index.js` | **ИСПОЛЬЗУЕТСЯ.** Это наш хостинг |
| **Cloudflare Pages** | Был хостингом по замыслу | **НЕДОСТУПЕН.** Cloudflare убрал создание новых проектов |
| **Cloudflare KV** | Задумывался как хранилище накопленной истории | **ОТКАЗАЛИСЬ.** Заменён на Turso |
| **Turso** | Хранилище накопленной истории (облачный SQLite) | **ИСПОЛЬЗУЕТСЯ** вместо KV |

Проще говоря: **Cloudflare — это хостинг, Turso — это база данных.** Раньше
предполагалось, что и то и другое даст Cloudflare, но его база (KV) не подошла
по лимитам, поэтому базу взяли у другого провайдера, а хостинг остался за
Cloudflare — только не Pages, а Workers.

### Почему Worker, а не Pages Function (август 2026)
Pages-проект создать невозможно: в панели остался только диалог «Create a
Worker». Поэтому единственный файл `functions/api/history/[plate].js` переписан
в обычный воркер `worker/index.js`.

Cloudflare предлагает компилировать папку `functions/` командой
`wrangler pages functions build`. **Мы этого не делаем:** маршрут ровно один,
точка входа была ровно одна, обвязка заняла полтора десятка строк. Это убирает
из конвейера шаг сборки, npm-зависимость и команду, которую сам Cloudflare
называет переходной. Логика Turso, рейт-лимит и формат ответа не менялись.

Ключевое следствие для раскладки: у Workers **ассеты отдаются до кода**, и
корнем сайта становится ровно одна папка. Поэтому статика лежит отдельно, в
`public/` — иначе `wrangler.jsonc` и `worker/` уехали бы в публичные файлы.
Адреса при этом не изменились: `/meta.json` и `/static/app.js` на прежних местах.

### Почему отказались от Cloudflare KV
На первом реальном прогоне заливка упала с ошибкой 429. Выяснилось: бесплатный
тариф KV разрешает **1000 операций записи в СУТКИ**, а машин у нас **2.4 млн**.
Разница в тысячи раз — залить базу было невозможно в принципе, не «медленно», а
именно никогда.

### Почему именно Turso
Перебрали варианты (все бесплатные тарифы):

| Вариант | Место | Лимит записи | Вердикт |
|---|---|---|---|
| Cloudflare KV | — | 1000/**сутки** | Не подходит вообще |
| Supabase | 0.5 ГБ | — | Мало места (у нас ~350 МБ и растёт ~130 МБ/год) |
| Neon | 0.5 ГБ | — | То же самое |
| Cloudflare D1 | 5 ГБ | 100 тыс./**сутки** | Первая заливка растянулась бы на ~25 дней |
| **Turso** | **5 ГБ** | **10 млн/МЕСЯЦ** | **Взяли.** 4.9 млн строк проходят за один прогон |

Бонус: Turso — это буквально SQLite, тот же диалект, что в локальной базе
сборщика. Схема и запросы переносятся почти один в один.

Важное техническое требование, которое отсекло часть кандидатов: серверная
функция Cloudflare работает на edge-рантайме и **не умеет открывать обычные
TCP-соединения к Postgres/MySQL**. Хранилищу обязательно нужен HTTP API.
У Turso он есть (`/v2/pipeline`).

## 2.3 Почему база не в git, а в GitHub Release
Локальная SQLite весит ~1.6 ГБ. GitHub блокирует push файлов больше 100 МБ,
а еженедельный коммит такого файла раздувал бы историю навсегда. GitHub Release
— лимит 2 ГБ на файл, вне истории git, без квоты трафика (в отличие от Git LFS).
Между прогонами база живёт там под тегом `db-latest`.

## 2.4 Почему JSON API, а не скачивание CSV
Изначально сборщик качал сырые CSV. Оказалось, CDN `e.data.gov.il` стоит за
защитой от ботов (JS-челлендж): обычный HTTP-клиент получает HTML-заглушку
вместо файла. Проверено вживую — в браузере тот же URL отдаёт нормальный CSV.

Решение: тянуть постранично через `datastore_search` — **тот же самый
официальный публичный API**, которым уже пользуется живой поиск. Это не обход
защиты, а другой штатный интерфейс того же портала.

## 2.5 Как устроена защита от массовой выгрузки

Постоянно действует:
- Данные лежат в Turso, к которой у браузера посетителя **нет прямого доступа**.
- Наружу торчит только `worker/index.js`, принимающий **ровно один номер за раз**.
  Эндпоинта «дай список» или «дай дамп» не существует в принципе.
- Потолок бесплатного тарифа Workers: **100 000 запросов в сутки**, сброс в
  полночь UTC, при превышении Error 1027 (проверено по документации Cloudflare).
  Перебрать 2.4 млн машин — это ~24 суток работы в потолок.

✅ **Рейт-лимит 25 запросов/мин на IP РАБОТАЕТ** — `RATE_LIMIT_DISABLED: "0"`
в `wrangler.jsonc`, возвращено 06.09.2026 после обнуления квоты Turso.

История, чтобы не пугаться при чтении старых коммитов: с 14.08 по 06.09 флаг
стоял в `"1"`, то есть **ограничения частоты не было вообще**. Причина — счётчик
пишется в Turso, а её месячная квота записей была превышена; исчерпание
блокирует **весь аккаунт**, то есть механизм защиты сам мог убить и сайт, и сбор
данных. Размен был осознанный: без счётчика худший случай мягче — выгорают
100 тыс. запросов Workers, сайт недоступен до полуночи и **чинится сам**.

Честная оценка: даже с включённым лимитом это **затрудняет и делает
нерентабельным** перебор, но не гарантирует невозможность (можно менять IP).
Так и записано в README.

Правильное решение на будущее — перенести ограничение из Turso в саму Cloudflare
(**WAF rate limiting rule**, на бесплатном тарифе доступен вариант со счётом по
IP): база тогда не участвует, и вывернутая логика исчезает насовсем. Загвоздка —
такие правила работают на уровне **зоны**, нужен свой домен в Cloudflare, а для
`*.workers.dev` они недоступны. Решение от 14.08: **домен не подключаем**,
остаёмся в бесплатном контуре и ждём 1 сентября.

## 2.6 Интерфейс на иврите
Аудитория ивритоязычная, и данные из data.gov.il **уже приходят на иврите**.
Поэтому весь UI на иврите, `<html lang="he" dir="rtl">`, CSS выправлен под RTL.
Словарь `VALUE_TRANSLATIONS` (иврит→русский) удалён намеренно — переводить
значения стало незачем, а это был источник ошибок.

**Комментарии в коде, README, FILES.md и этот файл остаются на русском** — это
заметки разработчику. Проверено автоматически: кириллицы в самом интерфейсе нет.

# 6. ГРАБЛИ, УЖЕ СОБРАННЫЕ (не наступать снова)

### 6.1 JOIN: обязателен `CAST(... AS TEXT)`
```sql
ON c.plate = CAST(CAST(TRIM(s.mispar_rechev) AS INTEGER) AS TEXT)
```
- **Внутренний `AS INTEGER`** срезает ведущие нули: из API приходит `07488339`,
  в базе лежит `7488339`. Без него такие машины КАЖДУЮ неделю считались бы новыми.
- **Внешний `AS TEXT`** нужен для скорости: без него сравнение TEXT-колонки с
  INTEGER-выражением не даёт использовать индекс, план вырождается в `SCAN`
  (2.4 млн × 2.4 млн) — прогон висел **16+ минут**. С ним — **1.5 секунды**.

Планы проверять через `EXPLAIN QUERY PLAN`, а не на глаз.

### 6.2 Массовые вставки — только внутри явной транзакции
`conn` открыт с `isolation_level=None`. Без явного `BEGIN` sqlite3 коммитит
каждую строку — миллионы fsync, часы простоя. Оборачивать в `db.transaction(conn)`.

### 6.3 staging-таблицы удалять + VACUUM
Иначе остаются навсегда и удваивают размер базы (было 1.19 ГБ вместо 600 МБ).
Удаляются в конце прогона (`drop_staging_tables`), **не** сразу после каждого
ресурса — `build_odometer_readings` джойнит `staging_history` со `staging_main`.

### 6.4 Дублирующие индексы
У `ownership` есть `PRIMARY KEY (plate, baalut_dt, baalut)` — отдельный индекс
по `plate` был бы дублем (leftmost prefix). Убран.

### 6.5 Основной реестр — только нужные поля
Все 24 колонки = ~2 ГБ RAM, рискованно для раннера. Запрашиваем 9 через
`fields=` → 418 МБ. См. `COLLECTED_RESOURCE_FIELDS` в `shared/refdata.py`.

### 6.6 Заливка в Turso: ретраи + возобновляемость
Упала на 940 тыс. из 4.87 млн с 502. Было две ошибки:
- ретраев не было (сотни запросов подряд — 502 практически неизбежна);
- курсор двигался только после ПОЛНОГО успеха → упавший прогон терял весь
  прогресс, следующий начинал с нуля и падал там же. Бесконечный цикл,
  сжигающий ~1 млн записей квоты за попытку.

Сейчас: до 5 попыток с растущей паузой, курсор пишется **после каждой пачки**.

### 6.7 Re-run в GitHub Actions берёт СТАРЫЙ коммит
«Re-run jobs» и «Re-run failed jobs» перезапускают тот же commit SHA. После
исправления кода нужен **свежий** запуск через «Run workflow».

### 6.8 Тип КПП по машине отследить нельзя
`automatic_ind` есть **только в каталоге моделей**, не в реестре по машине.
Это свойство модели, а не экземпляра — «поменяться» физически не может.
Ближайший честный сигнал — смена `degem_cd` (переклассификация), она отслеживается.

### 6.9 Перекупщик (סוחר) — не владелец
Транзитная точка, машина у него не эксплуатируется. Не получает номер руки,
километраж ему не считается. В таблице — обычная строка с пустой ячейкой руки.

### 6.10 Размер страницы API — не константа, а переменная (06.09.2026)
Портал data.gov.il может начать отбивать конкретную комбинацию
«ресурс + `limit`» **мгновенным 404** (0.1 с — отказ шлюза, не таймаут),
оставаясь при этом полностью работоспособным на другом `limit`. Замерено:

| Запрос | Результат |
|---|---|
| `main`, `limit=300000` | 200, 69 МБ, 6.4 с |
| `main`, `limit=500000` | **404 за 0.1 с** |
| `history`, `limit=500000` | 200, 111 МБ |

Поэтому `PAGE_SIZE` в `collector/api_loader.py` — стартовое значение, а не
жёсткое: `_fetch_page_adaptive` половинит страницу при отказе (до `MIN_PAGE_SIZE`)
и дальше идёт на том размере, который сработал. **Не «чинить» это обратно
в константу** — порог у портала уже один раз поехал и поедет снова.

Побочная польза: меньшая страница ещё и снижает пик памяти, а это была отдельная
забота на раннере GitHub Actions (см. §6.5).

### 6.11 Пагинация: короткая страница ≠ конец данных (06.09.2026)
Условие `if len(records) < PAGE_SIZE: break` выглядит как канонический способ
завершить пагинацию — и это **ловушка**. 24.08 портал отдал 32 000 строк
на запрос в 500 000, и сборщик принял обрезок за полный срез: записал его
в `snapshots` с честным sha256 и архивом, отличить от настоящего потом нельзя.

Для проекта, который сравнивает недельные срезы, тихий обрезок **опаснее
падения**: упавший прогон видно сразу, а испорченный снимок молча искажает
всю дальнейшую историю.

Правильно: `datastore_search` отдаёт `total` в каждом ответе — сдвигаться
на `len(records)`, а завершаться по `row_count >= total`, и **отказываться
записывать срез, если строк пришло меньше, чем `total`**.

Осознанный размен: если источник обновится ПРЯМО во время выкачки и строк
станет меньше, прогон упадёт на этом ресурсе. Это допустимо — ошибка попадёт
в лог и ресурс возьмётся на следующей неделе, тогда как тихий обрезок
не лечится вообще.

### 6.12 Две линии базы разошлись — их пришлось сливать (06.09.2026)
Сборщик работает в ДВУХ местах: локальная задача Windows (понедельник 06:00
по Израилю = 03:00 UTC) и GitHub Actions (03:00 UTC). Каждая ведёт **свою
копию базы** — локальную и ту, что лежит в GitHub Release.

Выглядит как «одно и то же с резервированием», но это не так. 17.08 локальная
задача сняла срез в 03:00 UTC, а CI — в 05:10 UTC, и **источник за эти два часа
успел обновиться**. С этого момента копии содержат разные факты, и ни одна
не включает другую:

| | Уникальных записей журнала |
|---|---|
| Только в Release (CI) | 3 629 |
| Только в локальной | 114 760 |

Среди 3 629 «маленьких» нашлись **14 скруток одометра и 1 смена двигателя** —
то есть именно то, ради чего проект существует. Одна из них: номер `23268201`,
385 640 → 158 132 км, минус 227 тысяч.

**Вывод на будущее: нельзя просто взять одну копию и затереть ею другую.**
06.09 линии слиты (скрипт разовый, в репозиторий не клался):
- снимки сопоставлены по `(resource_id, sha256)` — одинаковый хеш означает
  буквально один и тот же скачанный срез. Совпало 7 из 12, остальные 5
  перенесены и получили новые `snapshot_id`;
- записи перевешены на новые id снимков, иначе `snapshot_id` указывал бы
  на чужой срез (нумерация в двух базах независимая);
- пустышки `new_car` не переносились — они ничего не сообщают и стоят квоты.

Грабля внутри грабли: **дедупликация по `detected_at` не работает** — одно
и то же изменение получает разные метки времени в разных линиях, потому что
прогоны идут в разное время. Сравнивать надо по СУТИ (`plate`, `field`,
`old_value`, `new_value`). На первой попытке из-за этого в `history` уехало
64 361 дубля, их пришлось вычищать отдельно.

Как не наступить снова: держать копии в разошедшемся виде долго не надо.
Либо сливать регулярно, либо признать одну линию главной, а вторую считать
только резервом на случай отказа и не давать ей копить свою историю.

**Третья грабля, вылезшая уже из самого слияния: `snapshot_id` перестал идти
по хронологии.** Перенесённые снимки за 17 и 24 августа получили id 17-21,
то есть БОЛЬШЕ, чем у снимков от 6 сентября. А `last_snapshot_for` выбирал
последний срез запросом `ORDER BY snapshot_id DESC` — и начал возвращать
августовский обрезок на 32 000 строк как «последний».

Данные это не искажало (эталон сравнения берётся из `current_state`, а не из
снимка), но по `last_modified` последнего снимка решается, **тянуть ресурс или
пропустить**. Совпади там значение случайно — ресурс молча не собрался бы,
то есть ровно та поломка, которая уже стоила трёх недель.

Исправлено сортировкой по `taken_at`. Общий урок: **автоинкрементный id — не
метка времени.** Совпадение порядка держится ровно до первого восстановления
из копии, слияния или переноса, и полагаться на него нельзя.

### 6.13 Токен Turso в секретах GitHub умер молча (06.09.2026)
Первый прогон после включения заливки упал с **HTTP 401** на самом первом
обращении к Turso — ещё на `CREATE TABLE IF NOT EXISTS`. Секрет
`TURSO_AUTH_TOKEN` был заведён 14.08 и тогда работал (прогон #3 залил
1.63 млн строк), а к сентябрю перестал.

**Причина не установлена.** Пользователь уверен, что создавал токен без срока
истечения, так что версия «протух» не подтверждается. Возможные варианты —
отзыв при других действиях в аккаунте, миграция Turso на новую платформу,
лишний пробел в значении секрета. Лечится перевыпуском токена.

Что сбивает с толку при диагностике: **сайт в этот момент работал нормально.**
У Cloudflare лежит СВОЙ экземпляр токена, и он был живой. То есть «сайт читает
Turso» ничего не говорит о том, что заливка сможет туда писать — это два разных
токена в двух разных хранилищах секретов.

Как отличить от других отказов:
- **401** — токен не принят. URL при этом верный, иначе был бы 404/DNS.
- **502 + «SQL write operations are forbidden»** — токен read-only (§4.2, ловушка «в»).
- Проверить, жива ли сама база, можно платформенным токеном:
  `GET https://api.turso.tech/v1/organizations/komikagze/databases`.

Хорошая новость: **упавший прогон не стоил ни единицы квоты** — он лёг до
первой записи. Проверить новый токен «заранее» нельзя (секреты GitHub только
на запись), поэтому дешёвый способ проверки — просто запустить прогон.

### 6.14 Заливка должна быть наблюдаемой, иначе обрыв = потеря знания
Механизм блоков был правильный с самого начала: 10 000 строк на блок, курсор
в `sync_state` внутри Turso **после каждого блока**, `INSERT OR REPLACE`,
5 ретраев. Обрыв прогресс не терял.

Но 14.08, когда прогон отменили на середине, **никто не мог сказать, где он
остановился**: питон в CI запускался без `-u`, вывод буферизовался, и строки
перед принудительным завершением до лога не доехали. Лог обрывался на 08:34,
а прогон работал до 08:40 — шесть минут и ~218 тыс. строк оказались невидимы.

Исправлено 06.09: `python -u` во **всех трёх** шагах CI, плюс лог теперь несёт
- **план до первой записи**: сколько строк, сколько блоков, во сколько единиц
  квоты обойдётся (считается локально, квоту не тратит);
- **курсор в каждой строке прогресса** — точка возобновления видна прямо
  в логе, без похода в базу;
- **итоговые курсоры** в конце.

Урок шире, чем про этот скрипт: **механизм восстановления бесполезен, если
после аварии нельзя узнать, до какого места дошли.** Наблюдаемость — часть
механизма, а не украшение к нему.

# 8. ХРОНОЛОГИЯ: как мы сюда пришли

Полезно, чтобы понимать, почему код выглядит именно так.

**Исходная точка.** Проект был написан «вслепую» — файл за файлом, без
единого запуска кода. Интерфейс был на русском. Задача звучала так: перевести
интерфейс на иврит, впервые реально запустить, проверить и запушить на GitHub.

**1. Перевод на иврит.** UI переведён, `dir="rtl"`, CSS выправлен, словарь
иврит→русский удалён за ненадобностью.

**2. Первый запуск сборщика — падение.** Скачивание CSV отдавало HTML вместо
данных. Разобрались: CDN за анти-бот защитой. Переписали на постраничный JSON API.

**3. Второй запуск — зависание.** Висел 16+ минут без движения. Причина: вставки
без явной транзакции (миллионы отдельных коммитов). Обернули в транзакцию.

**4. База выросла до 1.19 ГБ.** Нашли две причины: staging-таблицы не удалялись
и дублирующий индекс. Почистили → 607 МБ.

**5. Не удалось запушить.** GitHub блокирует файлы >100 МБ. Решение: база уезжает
в GitHub Release, а не в git. Репозиторий стал 239 КБ.

**6. Первый прогон GitHub Actions — упал на заливке в Cloudflare KV** с 401.
Меняли токен, пересоздавали — не помогало.

**7. Вскрылась настоящая причина.** Письмо от Cloudflare: бесплатный KV — **1000
записей в сутки**, у нас 2.4 млн машин. Тупик по архитектуре, а не по токену.

**8. Выбор нового хранилища.** Пользователь: «всё должно быть бесплатно».
Перебрали Supabase, Neon, Cloudflare D1, R2, Backblaze, Google Drive. Проверили
актуальные лимиты по документации. Выбрали **Turso** (5 ГБ, 10 млн записей/мес,
и это SQLite). **Cloudflare Pages при этом остался хостингом.**

**9. Расширение данных по просьбе пользователя:**
- журнал изменений «когда / что / было → стало» с читаемыми названиями;
- пробеги **с датами техосмотров** — для этого пришлось дополнительно собирать
  основной реестр, потому что в ресурсе с километражом даты теста нет вообще;
- отслеживание полей реестра: цвет, VIN, тип владения, топливо, модель двигателя;
- разбор владения: перекуп не считается рукой, сроки владения, флаг перепродаж.

**10. По пути найдены и исправлены свои же баги:** сломанный JOIN по ведущим
нулям, потеря индекса из-за типов, 2 ГБ памяти на лишних колонках.

**11. Заливка в Turso упала на 940 тыс. строк** с 502. Исправлено: ретраи +
возобновляемый курсор. Запущен прогон #3, он идёт.
